# SwiftVR の「輪郭が太く・細く揺れる」現象：原因と対策

モザイク復元（BasicVSR++ などの一次復元）の後段に SwiftVR をかけてROIを高解像度化すると、フレームごとに輪郭が太くなったり細くなったりして見えることがあります。この文書では、その原因の確かめ方と対策を、ほかの環境で再現できる形でまとめます。

同じフォルダの `swiftvr_view_smoothing.py` が参考実装です（numpy と OpenCV だけで動き、OSに依存しません）。

---

## 1. 要点

- **原因**：SwiftVR 自体ではなく、SwiftVR に渡す切り出しの「見え方」がフレームごとに動いていることでした。
  - 検出の切り出し枠は、1フレームで最大約8%伸び縮みします。そのたびに、入力の中で被写体の位置や大きさがずれます。
  - 256px入力のうち切り出しの外側は、切り出しを鏡に映した絵で埋められています。この鏡の境目も、枠と一緒に動きます。
  - SwiftVR は、入力がずれるたびに輪郭を描き直します。そのため、輪郭の太さが毎フレーム変わります。
- **対策**：一次復元はそのままにします。SwiftVR に渡す時だけ、次のようにします。
  1. 切り出しの位置と拡大率を、前後15フレームの移動平均でなめらかにした枠で切り直す
  2. 切り出しの外側は、鏡の余白ではなく元フレームの周りの映像で埋める
  3. SwiftVR の出力は、元の枠に戻してから合成する
- **効果**（2x、12秒区間）：SwiftVR で増えた揺れは +5.2% から +1.0% になりました。一番ひどい秒では +58.8% から −11.6%（SwiftVR なしより少ない）です。質感は、一次復元比で 109.7% から 107.9% と、ほぼ維持できました。

---

## 2. 前提：SwiftVR は乱数を使わない

上流の SwiftVR（検証したのは commit `dbec2f99`）の推論は、1ステップだけです。

```
den = lq - DiT(lq, t = 1000)          # swiftvr/streaming/dit.py
```

- ノイズのサンプリングはなく、エンコーダ（TAE）も決定的です。ドロップアウトも推論時は 0 です。
- 同じ入力なら、出力は毎回同じになります。私たちの Core ML 移植版でも、ビット単位で一致しました。
- つまり、フレーム間の揺れは乱数から来るものではありません。**入力の小さな違いに対する SwiftVR の反応**から来ています。

---

## 3. 原因の確かめ方（プローブ実験）

実際の一次復元結果から、256px のROIを1枚取り出します。そこから48フレームの入力を4種類作り、SwiftVR（2x）に通します。

| 入力 | 作り方 | 入力の変化 | SwiftVR が足した分の変化 |
|---|---|---|---|
| static | 同じ画像を48回 | 0 | 0.27 |
| noise | 各フレームに N(0, 0.5/255) を足す | 0.56 | 0.45 |
| scale3 | 元フレームから、大きさを U(0.97, 1.03) で揺らして切り直す | 1.33 | **1.32（static の約5倍）** |
| shift1 | ±1px の小数ずらし | 0.75 | **0.81（約3倍）** |

- 数値は、フレーム間の平均絶対差（8bit 換算の階調）です。
- 「足した分」は、`出力 − 入力を出力サイズに双線形拡大したもの` です。
- `probe_sequences()` と `added_detail_change()` が、この実験の実装です。

**分かること**
- SwiftVR は、止まった入力には安定していて、細かいノイズも増幅しません。
- 一方、**入力の位置・大きさのずれには敏感**で、描き足す輪郭が大きく変わります。
- 4フレーム周期（ReAE の時間圧縮単位）の揺れは、ほとんど見られませんでした。

---

## 4. 切り出しの座標の決まり（lada 方式）

これは私たちのパイプラインの場合です。あなたの実装の決まりに合わせて置き換えてください。**入力の中の「見え方」がフレームごとに動くかどうか**が本質です。

1. シーン（クリップ）内の各フレームに、切り出し枠 `(left_i, top_i, width_i, height_i)` があります。
2. クリップで共通の拡大率を使います：`k_x = N / max_i(width_i)`、`k_y = N / max_i(height_i)`（N = 256）。
3. リサイズ後の大きさは `w'_i = floor(width_i·k_x)`、パディングは `pad_i = ceil((N − w'_i)/2)` です（y も同様）。
4. 格子の外側は、切り出しの**反射（鏡）**で埋めます。
5. 切り出しの内側では、格子の中心 g と画面座標 x は、次の一次式で対応します。

```
g = s_i · x + o_i
s_i = w'_i / width_i
o_i = pad_i − 0.5 − (left_i − 0.5) · s_i        （y も同様）
```

拡大率はクリップ内でほぼ一定ですが、**`o_i` はフレームごとに大きく動きます**（枠の伸び縮みと中心合わせのため）。検証したクリップでは、枠の幅が 339〜1340px の間で変わり、1フレームでの幅の変化は平均2.9%、最大8%程度でした。拡大率がクリップで最大の枠に合わせてあるので、小さい枠のフレームでは格子の大半が鏡の余白になります。

---

## 5. 対策の手順

`swiftvr_view_smoothing.py` の関数名を付けています。

1. **各フレームの対応を求める**（`clip_crops`, `placement`）
   各フレームの `(s_x, o_x, s_y, o_y)` を求めます。
2. **なめらかにする**（`smooth_placements`, window = 15）
   4つの値それぞれに、中心付きの移動平均（前後7フレーム、クリップの端では窓を切り詰める）をかけ、`(s̄, ō)` とします。
3. **SwiftVR 用の入力を作る**（`reframe`）
   なめらかにした格子の各画素 g̃ について、次のように値を決めます。
   - 画面座標 `x = (g̃ − ō)/s̄` を求め、そのフレーム本来の格子座標 `g = s·x + o` に変換します。
   - 値は `w · R_i(g) + (1 − w) · F_i(x)` とします。R_i は一次復元の格子（双線形で取る）、F_i は元フレーム（双線形で取る）です。
   - w は、切り出しの内側で1、外側で0とし、ふちから4格子画素かけてなめらかにつなぎます。

   ```
   w = clamp((d + 0.5) / 4, 0, 1)
   d = min(g − pad, pad + w' − 1 − g)      （x と y の積）
   ```
4. **SwiftVR にかける**：得られた列をそのまま SwiftVR に渡します。
5. **元の格子に戻す**（`map_back`）
   出力（M = N·倍率）の各画素 u について、次の位置の値を双線形で取ります。

   ```
   g  = (u + 0.5)/k − 0.5           （k = M/N）
   x  = (g − o)/s
   g̃ = s̄·x + ō
   取る位置 = (g̃ + 0.5)·k − 0.5
   ```
6. **合成**：この後の処理（前後フレームとのなじませ、色合わせ、ROIへの合成）は、今までと同じです。

**参考実装の自己テスト**
- `python swiftvr_view_smoothing.py` を実行すると、手順3→5の往復で元の格子に戻るかを確かめます。
- 私たちの環境では、誤差は平均0.55階調（双線形補間2回分のぼけ）でした。手順5を省くと7.45階調になるので、ずれは確実に分かります。

## 6. 評価のしかた

比べるのは、次の3本の書き出しです。
- **B**：SwiftVR なし（一次復元だけ）
- **A**：今の方式
- **S**：対策後

1. **範囲**（`dense_mask`）：輝度 `|A − B|` を 15×15 で平均し、3階調を超える所だけを使います。
   - 別々にエンコードした動画どうしでは、画素ごとの差だけで範囲を決めると、画面全体に散らばるエンコードの差を拾ってしまいます。
   - 実際に私たちも最初はこれを拾ってしまい、効果を過大に見積もりました。
2. **揺れ**（`flicker_increase`）：範囲の中で、時間方向の2階差分 `|X[t+1] − 2X[t] + X[t−1]|` を平均します。
   - 範囲が5000画素以上のフレームだけ合計します。
   - Bとの比から1を引いた値（%）を出します。「SwiftVR で何%揺れが増えたか」です。
3. **質感**（`texture_ratio`）：範囲の中で `|G_σ1(X) − G_σ3(X)|`（おおむね1〜3画素の輪郭・質感）を平均し、Bとの比（%）を出します。

---

## 7. 結果（2x、12秒区間）

条件：一次復元 BasicVSR++、SwiftVR 2x。後段に、前後1フレームのなじませ、色合わせ、時間方向ノイズ除去（強さ1.0）あり。

| 区間 | 今の方式 | 対策後 |
|---|---|---|
| 53秒 | +9.8% | −1.5% |
| 54秒 | +54.5% | −9.3% |
| 55秒 | +58.8% | −11.6% |
| 12秒全体の揺れ | +5.2% | **+1.0%** |
| 12秒全体の質感 | 109.7% | 107.9% |
| 別の12秒クリップの揺れ | +1.5% | −0.3% |

**なめらかにするフレーム数**（プローブ、75フレーム）

| フレーム数 | 揺れ | 質感 |
|---|---|---|
| 1（今の方式） | +46% | 101.6% |
| 7 | +2.4% | 105.0% |
| **15** | **−8.2%** | **108.6%** |
| 31 | −9.3% | 105.5% |
| 1つの大きな固定枠 | −16.1% | 101.4% |

---

## 8. 注意点・分かっていること

- **周りの映像で埋めるのが重要です。** 枠をなめらかにするだけで余白を鏡のままにすると、一番ひどい秒の改善は +47% → +36% 程度でした。周りの映像で埋めて、初めて −8% になりました。
- **一次復元の枠まで平均するのは逆効果でした**（別の検証）。なめらかにするのは、SwiftVR に渡す見え方だけにしてください。
- **動きの大きい場面では効果が小さめ**で、1秒だけ悪化した所もありました（60秒付近で +2.8% → +6.1%）。
- 後段の時間方向ノイズ除去は、細かいざらつきには効きますが、この輪郭の揺れには効きません。
- 数値は、1本の作品の数区間での測定です。あなたの素材では、まず第3節のプローブで、SwiftVR が入力のずれに敏感かどうかを確かめるのがおすすめです。
